## Core concept

A PD controller knows nothing about the robot: it reacts to errors after they appear. Model-based control uses the equations of motion of Level 7 to supply the torque the motion needs before an error appears, and leaves feedback to correct what the model gets wrong. Three ways of doing it, in order of how much they trust the model:

- **Gravity compensation** adds the bias force at the current state. It removes the steady pull of gravity (Lesson 8.1) and nothing else.
- **Inverse-dynamics feedforward** adds the torque the planned motion requires, $M(q^\star)\ddot q^\star + c(q^\star, \dot q^\star)$, computed along the plan. Feedback is still a plain PD.
- **Computed torque** (feedback linearization) uses the model inside the feedback loop: $\tau = M(q)\,(\ddot q^\star + K_p e + K_d\dot e) + c(q, \dot q)$. With an exact model every joint becomes an independent unit mass driven by its own PD.

The question this lesson measures is what each one buys when the model is right, and what each one costs when it is wrong.

> [!established] The ingredients in MuJoCo
> At any state, `mj_forward` provides `qfrc_bias` (gravity, Coriolis and centrifugal) and the mass matrix through `mj_fullM`; `mj_inverse` provides the whole inverse dynamics, including passive forces (Lesson 7.2). A controller model is just another `MjModel`: edit its masses and call `mj_setConst` to give a controller a deliberately wrong model while the simulated robot keeps the true one.

## Visual intuition

## Mathematics

### What each controller leaves to the feedback

Write the true dynamics as $M\ddot q + c = \tau$ (with damping folded into $c$) and the controller's model as $\hat M$, $\hat c$. With the PD part $u = K_p e + K_d \dot e$ and $e = q^\star - q$:

- **PD**: $M\ddot q + c = u$. The feedback must produce all of $M\ddot q^\star + c$, which it can only do by keeping an error.
- **Gravity compensation**: $\tau = u + \hat c(q, \dot q)$. The error must still produce the inertial torque $M\ddot q^\star$.
- **Feedforward**: $\tau = u + \hat M(q^\star)\ddot q^\star + \hat c(q^\star, \dot q^\star)$. Near the plan, the error dynamics are $M\ddot e + K_d\dot e + K_p e \approx (M - \hat M)\ddot q^\star + (c - \hat c)$: the model error enters as a disturbance, and the feedback gains are untouched.
- **Computed torque**: $\tau = \hat M(\ddot q^\star + K_pe + K_d\dot e) + \hat c$. With an exact model, $\ddot e + K_d\dot e + K_pe = 0$ for every joint. With $\hat M = sM$ (all link masses scaled by $s$, ignoring armature), the closed loop becomes $\ddot e + sK_d\dot e + sK_pe = (1-s)\ddot q^\star + \ldots$: the model error scales the feedback gains as well as adding a disturbance.

> [!derivation] Why computed torque suffers more from an underestimated mass
> With $s = 0.5$, computed torque loses both ways: half the needed feedforward and half the intended stiffness, so its effective bandwidth drops from 20 to about 14 rad/s while the disturbance it must reject doubles. Feedforward keeps its full PD gains and only loses part of the feedforward. With $s = 1.5$, computed torque is over-stiff instead of under-stiff, and the extra gain partly offsets the disturbance: output shows 5.6 mrad against 15.3 for $s = 0.5$, an asymmetry the linear argument predicts.

### Fair comparison

All four controllers use the same feedback bandwidth: PD gains $k_{p,i} = M_{ii}\,\omega_n^2$ and $k_{d,i} = 2\zeta M_{ii}\omega_n$ from each joint's inertia at home, and unit-mass gains $\omega_n^2$, $2\zeta\omega_n$ inside computed torque, with $\omega_n$ = 20 rad/s and $\zeta$ = 1. Comparing controllers at different gains would measure the gains, not the model.

```python file=examples/l8_2_model_based.py
"""Lesson 8.2: gravity compensation, feedforward and computed torque on the 7-DOF arm.

INPUT   arm7.xml (torque motors with limits); a controller model whose link masses and
        inertias are scaled by s (s = 1 is the true model), sharing the true armature
PROCESS track q*(t) = home + A sin(2 pi f t) for 4 s with four controllers that use the
        same feedback bandwidth:
          PD                  tau = Kp e + Kd edot
          PD + gravity        ... + qfrc_bias of the controller model (current state)
          PD + feedforward    ... + inverse dynamics of the plan, M(q*) qdd* + c(q*, qd*) + b qd*
          computed torque     tau = M(q) (qdd* + wn^2 e + 2 wn edot) + c(q, qdot) + b qdot
        for s = 1, 0.5 and 1.5, and report RMS and peak joint error after the first second
OUTPUT  a table of tracking errors and torque saturation

Run:  python examples/l8_2_model_based.py
"""

import mujoco
import numpy as np

from mjcourse import model_path

WN, ZETA = 20.0, 1.0                                     # feedback bandwidth (rad/s) and damping ratio
AMP = np.array([0.3, 0.2, 0.3, 0.3, 0.4, 0.3, 0.5])      # rad
FREQ, DURATION, SKIP = 0.5, 4.0, 1.0                     # Hz, s, s (error statistics start after SKIP)


def controller_model(scale: float) -> tuple[mujoco.MjModel, mujoco.MjData]:
    """arm7 with every link's mass and inertia scaled; armature and damping are the motors' and stay."""
    model = mujoco.MjModel.from_xml_path(str(model_path("arm7")))
    model.body_mass[1:] *= scale
    model.body_inertia[1:] *= scale
    data = mujoco.MjData(model)
    mujoco.mj_setConst(model, data)
    return model, data


def plan(home: np.ndarray, t: float):
    w = 2 * np.pi * FREQ
    return home + AMP * np.sin(w * t), AMP * w * np.cos(w * t), -AMP * w**2 * np.sin(w * t)


def full_mass(model, data) -> np.ndarray:
    m = np.zeros((model.nv, model.nv))
    mujoco.mj_fullM(model, data, m)
    return m


def home_inertia(home: np.ndarray) -> np.ndarray:
    """Diagonal of the true mass matrix at home: each joint's inertia with the others held."""
    model, data = controller_model(1.0)
    data.qpos[:] = home
    mujoco.mj_forward(model, data)
    return np.diag(full_mass(model, data))


def track(kind: str, scale: float) -> tuple[float, float, float]:
    model = mujoco.MjModel.from_xml_path(str(model_path("arm7")))
    data = mujoco.MjData(model)
    home = model.key_qpos[model.key("home").id].copy()
    cmodel, cdata = controller_model(scale)
    m_home = home_inertia(home)
    kp, kd = m_home * WN**2, 2 * ZETA * m_home * WN          # per-joint gains from the home inertia
    damping = model.dof_damping
    data.qpos[:] = home
    data.qvel[:] = plan(home, 0.0)[1]
    limit = model.actuator_ctrlrange[:, 1]
    errors, saturated, h = [], 0, model.opt.timestep
    for k in range(round(DURATION / h)):
        t = k * h
        q_d, qd_d, qdd_d = plan(home, t)
        e, edot = q_d - data.qpos, qd_d - data.qvel
        if kind == "PD":
            tau = kp * e + kd * edot
        elif kind == "PD + gravity":
            cdata.qpos[:], cdata.qvel[:] = data.qpos, data.qvel
            mujoco.mj_forward(cmodel, cdata)
            tau = kp * e + kd * edot + cdata.qfrc_bias
        elif kind == "PD + feedforward":
            cdata.qpos[:], cdata.qvel[:] = q_d, qd_d             # the model evaluated along the plan
            mujoco.mj_forward(cmodel, cdata)
            tau = kp * e + kd * edot + full_mass(cmodel, cdata) @ qdd_d + cdata.qfrc_bias + damping * qd_d
        else:                                                    # computed torque
            cdata.qpos[:], cdata.qvel[:] = data.qpos, data.qvel
            mujoco.mj_forward(cmodel, cdata)
            v = qdd_d + WN**2 * e + 2 * ZETA * WN * edot
            tau = full_mass(cmodel, cdata) @ v + cdata.qfrc_bias + damping * data.qvel
        saturated += int(np.any(np.abs(tau) > limit))
        data.ctrl[:] = tau
        mujoco.mj_step(model, data)
        if t >= SKIP:
            errors.append(plan(home, t + h)[0] - data.qpos)
    err = np.array(errors)
    return float(np.sqrt(np.mean(err**2))), float(np.abs(err).max()), saturated * h


if __name__ == "__main__":
    print(f"track home + A sin(2 pi {FREQ} t), A = {AMP.tolist()} rad, for {DURATION} s; feedback bandwidth "
          f"{WN} rad/s, damping ratio {ZETA}; errors after the first {SKIP} s")
    print(f"  {'controller':<18}{'model scale':>12}{'RMS error (mrad)':>18}{'peak error (mrad)':>19}{'time saturated (s)':>20}")
    for kind in ("PD", "PD + gravity", "PD + feedforward", "computed torque"):
        for scale in ((1.0,) if kind == "PD" else (1.0, 0.5, 1.5)):
            rms, peak, sat = track(kind, scale)
            label = "-" if kind == "PD" else f"{scale:g}"
            print(f"  {kind:<18}{label:>12}{1000 * rms:>18.2f}{1000 * peak:>19.2f}{sat:>20.3f}")
```

Reading the output:

- **With the true model**, gravity compensation removes about 40% of PD's RMS error (26 to 16 mrad); what remains is the inertial torque of the motion. Feedforward and computed torque both remove almost all of it: 0.20 and 0.17 mrad, more than a hundredfold better than PD at the same feedback gains.
- **With a wrong model**, feedforward degrades symmetrically, to 11 mrad for masses halved or increased by half. Computed torque degrades asymmetrically: 15 mrad when the model is too light, 5.6 mrad when it is too heavy, for the reason derived above. Gravity compensation is hurt least in absolute terms because it relied on the model least.
- No controller saturated: these differences come from the control laws, not the motor limits.

> [!recommendation] Choosing between them
> Feedforward along the plan is the robust default when a trajectory is known in advance: it gets almost all of computed torque's accuracy when the model is right and keeps the feedback you tuned when it is wrong. Computed torque is the right tool when the trajectory is not known ahead (reactive or task-space control) and the model is trustworthy; if mass is uncertain, err towards overestimating it.

## Debugging

**Tracking is good on the bench and poor with a payload.** The payload changes $M$ and $c$; a model-based controller that does not know about it behaves like the $s \ne 1$ rows. Add the payload to the controller model, or identify it (Level 18).

**Computed torque oscillates when the model is changed.** The model error also changes its feedback gains (Mathematics). Check the effective stiffness, $\hat M M^{-1}K_p$, not just $K_p$.

**Gravity compensation drags a moving arm.** `qfrc_bias` includes Coriolis and centrifugal terms: correct for full compensation of the current state, but if the state estimate is noisy, so is the compensation. Filter velocities or compensate gravity alone (Lesson 7.1, Debugging).

**Feedforward helps at slow speeds and hurts at high ones.** The plan's acceleration is not achievable within the torque limits, so the feedforward saturates. Check $|\tau|$ against `ctrlrange` along the plan before running it.

## Research connection

> [!research] Residual learning on top of a model
> Learned controllers for real robots often take this lesson's best structure and learn only the residual: a model-based feedforward or computed-torque term, plus a learned correction for what the model misses (friction, payload, unmodelled actuator dynamics). The table above suggests why the split matters: when the model is right, feedforward leaves almost nothing to learn; when it is wrong in a structured way (a scale on the masses), the residual has a simple form that a correction can learn from little data (inference).
